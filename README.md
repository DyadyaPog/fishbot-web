# FishBot — кабинет игрока

Сайт для зрителей Twitch-канала с рыбалкой в чате. Одна страница с входом через
Twitch: зритель видит свой баланс, уровень и уловы, разбирает инвентарь, надевает
снаряжение и смотрит рейтинг канала. Сама игра идёт в чате через бота, сайт — личный
кабинет к ней.

## Разделы

| Раздел | Что показывает |
|---|---|
| Канал | Выбор канала, на котором рыбачил игрок: у каждого канала своя статистика и свой инвентарь |
| Профиль | Баланс, уровень, полоса опыта до следующего уровня, последние уловы |
| Инвентарь | Все предметы игрока: тип, редкость, количество; фильтры по типу и редкости, поиск по названию |
| Экипировка | Слоты удочки, лески, крючка и наживки — надеть и снять можно прямо на сайте |
| Магазин | Витрина снаряжения по шести страницам редкости и отдельный магазин артефактов, пока бот открыл его окно |
| Рейтинг | Топ игроков канала по балансу и уровню |
| Бот на канале | Стример подключает бота к своему каналу и отключает его — без правки `.env` и без перезапуска бота |

## Как устроен

- Чистая статика без сборки: `index.html`, `assets/style.css`, `assets/app.js`, `config.js`.
- Канал не задаётся в `config.js`: после входа страница получает список каналов, где у
  игрока есть данные, и показывает выбранный. Выбор запоминается в `localStorage`.
- Данные — из Supabase (Postgres) той же базы, что использует бот: страница ничего не
  хранит у себя и не дублирует игровую логику. Данные разделены по каналам.
- Экипировка меняет флаг `is_equipped` у предмета, и бот учитывает её в следующей рыбалке.
- Магазин артефактов открывает только бот: окно лежит в `shop_state`, кабинет получает его через Realtime, подсвечивает пункт «Магазин» и показывает плашку, если магазин открыт на другом канале. Покупка идёт через `buy_item` / `buy_artifact`, поэтому уровень, деньги и занятый тип артефакта проверяет база.
- Подключение бота — вкладка «Бот на канале». Стример входит через Twitch и нажимает
  «Подключить бота»: RPC `request_bot_channel` создаёт заявку только для канала, чей
  Twitch ID совпадает с ID вошедшего (свой канал есть у каждого пользователя Twitch,
  поэтому подставить чужой нельзя). Бот раз в минуту читает `channels` и сам входит
  в чат нового канала, после чего переводит заявку в `active`. «Отключить бота»
  ставит `disabled` — бот выходит из чата, а баланс, инвентарь и уловы остаются.
  Владелец бота может поменять статус канала и забанить стримера в админ-панели
  (шаг 46): забаненный канал бот покидает и больше не подключает, а снять
  блокировку из кабинета нельзя.
- Авторизация бота — отдельный вход через Twitch для значка чат-бота. Кнопка
  «Авторизовать бота» уводит на страницу Twitch, где стример разрешает
  приложению бота `channel:bot`. Кабинет не хранит токен: он только сообщает
  боту, что можно перепроверить авторизацию (шаг 46). `badge_at` ставит сам бот
  после успешной отправки через Send Chat Message с app-токеном — это и есть
  реальное подтверждение, что значок работает. Альтернатива без авторизации —
  выдать боту модератора канала: значок показывается модераторам.
- Без входа открывается гостевой экран; кнопка «Демо-режим» показывает кабинет с
  примером данных.
- Дизайн повторяет стилистику админки бота: тёмная тема, сайдбар, карточки, тосты.

## Запуск

```bash
python -m http.server 4173
```

Открыть `http://localhost:4173/`. Открывать `index.html` файлом нельзя: браузер не
подгрузит `config.js` и `assets/*`.

## Настройка

`config.js`:

```js
window.FISHBOT_CONFIG = {
    supabaseUrl: '',        // Project URL из Supabase
    supabaseAnonKey: '',    // anon key (публичный, при настроенном RLS)
    twitchBadgeUrl: '',     // адрес Edge Function авторизации бота (публичный)
    schemaVersion: 7        // 7 — значок чат-бота (badge_at, шаг 46)
};
```

Пока URL и ключ пустые, работает только демо-режим. При публикации значения можно
задать repository variables `SUPABASE_URL`, `SUPABASE_ANON_KEY` и `TWITCH_BADGE_URL` —
workflow подставит их в `config.js` при деплое. Переменная канала не нужна.

### Авторизация бота (значок чат-бота)

1. Авторизацию ведёт Edge Function `supabase/functions/twitch-badge`: она сама
   уводит на Twitch, принимает обратно одноразовый `code`, меняет его на токен
   своим `client_secret`, проверяет `channel:bot`, отзывает токен и пишет
   `channels.bot_badge_requested_at`. Секрет и сервисный ключ есть только у
   функции: в статике их нет, в браузере нет ни токена, ни `code`.
2. Разверните функцию и задайте секреты (значения — только в Supabase):
   `supabase functions deploy twitch-badge --no-verify-jwt` и
   `supabase secrets set TWITCH_CLIENT_ID=... TWITCH_CLIENT_SECRET=... CABINET_URL=https://<user>.github.io/<repo>/ BADGE_STATE_SECRET=<случайные 32+ байта>`.
   `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` функция получает от платформы.
   `BADGE_REVOKE_TOKEN=0` отключает отзыв токена — только если Twitch начнёт
   снимать разрешение после отзыва (по умолчанию токен отзывается сразу).
3. В **OAuth Redirect URLs** приложения бота добавьте точный адрес функции:
   `https://<project-ref>.supabase.co/functions/v1/twitch-badge`. Twitch требует
   полного совпадения. Кабинет в этом списке не нужен: возврат идёт на функцию, а
   она перекидывает стримера на `CABINET_URL` с `?badge=ok|denied|nochannel|...`.
4. В repository variable `TWITCH_BADGE_URL` укажите тот же адрес функции —
   workflow подставит его в `config.js` как `twitchBadgeUrl`.
5. Токен аккаунта бота должен быть выдан с `user:bot` и `user:write:chat`
   (в `.env` это `TWITCH_ACCESS_TOKEN` / `TWITCH_REFRESH_TOKEN`). Без `user:bot`
   Send Chat Message не даст значок, даже если стример выдал `channel:bot`.
6. Стример нажимает «Авторизовать бота» на вкладке «Бот на канале».
   Альтернатива без авторизации — сделать бота модератором канала: значок
   показывается и модераторам.

## Данные в Supabase

- Таблицы `channels`, `accounts`, `players`, `inventory`, `catches`, `events`, `shop_state`;
  справочник `items` закрыт для клиентов — кабинет читает вьюху `items_public`
  с витринными колонками, `artifact_catalog` доступен только функциям; views
  `my_channels` (каналы игрока) и `channel_ranking` (топ канала). Строки
  привязаны к каналу, поэтому один игрок может иметь разные балансы, уровни и инвентари
  на разных каналах.
- Схема и наполнение — SQL-скрипты в `supabase/`; данные из SQLite переносит
  `fishBot/scripts/migrate-to-supabase.mjs` (`npm run db:migrate`).
- Подключение бота, админ-управление каналом и баном, значок `channel:bot`,
  Twitch ID из `auth.identities` и колоночные гранты `channels` собраны в одном
  шаге `46_bot_access_and_hardening.sql` (объединяет бывшие 46–50). Отдельные
  файлы 47–50 удалены: запускать нужно только шаг 46, иначе порядок миграций
  разойдётся. Колонки `channels.owner_auth_id`, `bot_status`, `bot_requested_at`,
  `bot_joined_at`, `bot_banned`, `bot_badge_requested_at`, `bot_badge_at` и RPC
  `my_bot_channel`, `request_bot_channel`, `disable_bot_channel`,
  `admin_set_bot_channel` создаются этим же шагом. `request_bot_badge_access`
  остаётся в базе, но с шага 47 доступна только `service_role`: кабинет
  авторизует бота через Edge Function twitch-badge, а bot_badge-поля пишет
  только функция под service-role.
  Статус `active` ставит бот после реального входа в чат (вручную — только
  админ-панель владельца); кабинет не может «нарисовать» работающего бота.
  `claim_profile` берёт Twitch ID из `auth.identities`, поэтому его нельзя
  подделать через редактируемую `raw_user_meta_data`. Кабинет читает из
  `channels` только `id`, `login`, `display_name`; `owner_auth_id` и служебные
  статусы бота закрыты.
- Шаги применяются строго по порядку номеров. Первым — `00_schema_migrations.sql`:
  он ведёт учёт применённых файлов, и каждый следующий шаг начинается с
  `assert_migration(...)`. Повторный запуск старого файла (например,
  `17_buy_artifact.sql` после `23_shop_state.sql`) падает, а не откатывает
  свежие правки. На базе, где шаги 01–23 уже есть, после `00` выполните
  `00b_backfill_migrations.sql`, затем `24_hardening.sql`.
- Провайдер Twitch в **Authentication → Providers**.
- В **Authentication → URL Configuration**:
  - **Site URL** — куда Supabase вернёт вход, если адрес не разрешён. Дефолтный
    `http://localhost:3000` — причина, по которой после Twitch открывается он.
  - **Redirect URLs** — точные адреса страницы: `http://localhost:4173/` и
    `https://<user>.github.io/<repo>/` (можно `https://<user>.github.io/<repo>/**`).
    Страница передаёт свой текущий адрес в `redirectTo`; не попавший в этот список
    адрес подменяется на Site URL.
- При первом входе `claim_profile()` связывает Twitch ID с `auth.users.id`; дальше
  страница читает `my_channels`, `inventory`, `catches`, `channel_ranking` под RLS.
- RLS: игрок читает только свои строки; экипировка — через RPC `equip_item` /
  `unequip_item` с проверкой владельца.
- `shop_state` виден только по своим каналам: чужое окно магазина не отдаётся.
- `channel_ranking` не содержит Twitch ID — рейтинг строится по нику и балансу.

## Безопасность

- В `index.html` стоит строгая CSP без `'unsafe-inline'` для скриптов: обработчики
  висят на `data-*`-атрибутах, а не в `onclick`. Свой домен Supabase нужно добавить
  в `connect-src`, иначе запросы заблокирует браузер.
- Изменения из кабинета лимитированы в базе (`24_hardening.sql`): 30 операций с
  балансом и 60 операций с инвентарём в минуту, пересчёт шансов — 3 раза в 5 минут.
  Бот работает `service_role` и под лимиты не попадает.
- При авторизации бота Twitch возвращает access token во фрагменте URL.
  Кабинет сразу убирает его из адреса и никуда не сохраняет — боту уходит
  только отметка «перепроверь авторизацию», а реальный результат подтверждает
  успешная app-отправка. Токен бота и client secret в браузер не попадают.
- Действия админ-панели бота пишутся в `admin_audit_log`.
